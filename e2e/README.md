# e2e smoke tests

Automated smoke tests that run the example app (`example/`) on a simulator or emulator. Each script prints PASS, FAIL or SKIP for every case. The exit code is non-zero if any case fails.

<!-- ios:start -->
## iOS (Simulator)

```sh
./e2e/ios.sh                                # build (Release), boot headless, run 5 cases, shut down
SKIP_BUILD=1 ./e2e/ios.sh                   # reuse last build
SIM_NAME="iPhone 15 Pro" SIM_OS=17 ./e2e/ios.sh
SIM_UDID=<udid> KEEP_SIM=1 ./e2e/ios.sh
```

**Requirements:** Xcode, CocoaPods, a prebuilt `example/ios` (`cd example && npx expo prebuild -p ios`), and the [agent-device](https://github.com/callstackincubator/agent-device) CLI on `PATH` or in `AGENT_DEVICE`, used to tap testIDs. `idb` is optional and only used for the lock attempt.

**How it works**

- Builds with `xcodebuild` in **Release** by default. The JS bundle is embedded, so Metro isn't needed.
- Boots the simulator with `xcrun simctl boot` (Simulator.app is not opened). If the script booted the simulator, it shuts it down at the end.
- Reads console output from the unified log with `simctl spawn <udid> log stream`. In Release, `console.log` still reaches the log as `[com.facebook.react.log:javascript] [SDQA] ...`.
- Keeps logs, the xcodebuild log and the agent-device log under `~/Library/Caches/expo-screen-detector-e2e/artifacts/ios-<ts>/`. `ART_DIR` overrides this location.

**Building from iCloud Drive:** if the repo is under `~/Desktop` or `~/Documents` with iCloud "Desktop & Documents" sync on, iCloud tags build products with FinderInfo and fileprovider xattrs. `codesign` then fails with `resource fork, Finder information, or similar detritus not allowed`, first inside `expo-modules-jsi`'s nested xcodebuild. To avoid this, the script mirrors the repo with `rsync` to `~/Library/Caches/expo-screen-detector-e2e/repo`, runs `pod install` there (fast, from the CocoaPods cache) and builds in the mirror. `IOS_MIRROR=0` or `IOS_MIRROR=1` forces either mode.

**Cases**

| # | Case | PASS when |
|---|---|---|
| 1 | Build, install, launch | No "Cannot find native module", red box or `[SDQA] ERROR`. `bg-registered` is seen. An interval line reports `off=false locked=false unavailable=false` |
| 2 | Tap `btn-refresh` | A `src:"refresh"` line appears with the same values |
| 3 | Open Settings, wait 5 s, relaunch the app | The appState events go `inactive`, `background`, then `active`, the pid is unchanged and polling resumes |
| 4 | Tap `btn-trigger-bg` | **Expected SKIP.** See the limits below |
| 5 | Lock | **Expected SKIP.** There is no working headless lock (see below) |

**Simulator limits (by design, not bugs)**

- There is no passcode, so `isProtectedDataAvailable` is always `true` and `locked` is always `false`.
- `UIScreen.main.brightness` is fixed on the Simulator (0.5 is commonly reported), so `off` is always `false`.
- `BGTaskScheduler` doesn't run on the Simulator:
  - `expo-background-task` reports `Restricted` and skips registration with the warning *"Background tasks are not supported on iOS simulators"*. The example still logs `bg-registered`.
  - In Release, `triggerTaskWorkerForTestingAsync()` is `__DEV__`-only and returns `false`. `[SDQA-BG]` never fires.
- Lock:
  - `simctl` has no lock command and agent-device doesn't provide one.
  - `idb ui button LOCK` is attempted. With Xcode 27 it fails because `SimulatorKit.framework` isn't at the path idb_companion expects (`Xcode.app/Contents/Developer/Library/PrivateFrameworks`), so HID input doesn't work. The script only counts the lock as effective if the app's appState leaves `active`.

Lock, screen-off and background-task behavior must be tested on a real device. See [IOS_DEVICE_CHECKLIST.md](IOS_DEVICE_CHECKLIST.md).

## Android (Emulator)

```sh
cd example/android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a   # build once
./e2e/android.sh                                   # default device: emulator-5554
ANDROID_SERIAL=emulator-5556 APK=/path/app-release.apk ./e2e/android.sh
SKIP_INSTALL=1 E2E_LOG_OUT=/tmp/js.log ./e2e/android.sh
```

**Requirements:** `adb`, a running emulator or device with **no lock credential** (the script refuses to run otherwise, because it could not restore the credential), and a release APK. The JS bundle is embedded, so Metro isn't needed. `example/android` is generated by `npx expo prebuild -p android`.

**How it works**

- The property under test is the `SDQA_BG` background task (`expo-background-task`, which runs on WorkManager). JS timers stop while the app is in the background, so foreground polling can't observe screen-off.
- For each case, the script looks up the app's WorkManager job with `dumpsys jobscheduler`, then force-runs it with `cmd jobscheduler run -f <pkg> <jobId>`. It asserts on the `[SDQA-BG]` line that follows and only accepts lines whose `t` is at or after the force-run. It retries up to `JOB_ATTEMPTS` times and waits `JOB_WAIT` seconds for each attempt.
- Logcat (`ReactNativeJS` and `-b crash`) is streamed once to local files, because `logcat -d` can take tens of seconds on a loaded host.
- The script temporarily sets PIN `1234` (`PIN=` overrides it). An `EXIT` trap always unlocks the device in a single `adb shell` chain (the keyguard bouncer times out after about 10 s), runs `locksettings clear --old 1234`, restores `set-disabled true` if that was the initial state, and verifies both.

**Cases**

| # | State | Expected `[SDQA-BG]` |
|---|---|---|
| 1 | Install and launch | `bg-registered`, plus a foreground `[SDQA]` line with all values `false` |
| 2 | App backgrounded (HOME), screen on, no PIN | off=false locked=false unavailable=false |
| 3 | `KEYCODE_SLEEP`, no PIN | off=true locked=false unavailable=true |
| 4 | PIN set, screen off | off=true locked=true unavailable=true |
| 5 | PIN set, `KEYCODE_WAKEUP` at the keyguard (not unlocked) | off=false locked=true unavailable=true |
| — | Global checks | No `[SDQA-BG] ERROR` or `bg-register-error`, no app crash in `logcat -b crash`, PIN cleared |

**Notes:** with no PIN, this AVD has no keyguard at all (`locksettings get-disabled` is `true`), so `locked` only becomes true once a PIN is set. On a heavily loaded host, the emulator can ANR-kill the app during startup ("failed to complete startup"). Case 1 relaunches the app up to 3 times within `LAUNCH_WAIT` (180 s by default).
